# Local File Transfer

Send batches of 1–128 files from the device overview over an already-authenticated local-network or Bluetooth connection. Local network has priority whenever it is secured. The peer must advertise transfer support. Bluetooth is available when local network is disconnected; it is slower and uses the existing secured BLE session. The receiver approves each batch; files transfer sequentially with bounded cumulative credit.

Updated Android and Mac apps use LAN chunks up to 262,016 bytes with an authenticated 256-KiB record profile. Bluetooth retains 3-KiB chunks. Both apps must be updated to use the new transfer capability for larger chunks; older peers retain their negotiated limits. Native identity and trust checks remain live. See the [LAN profile contract](../../protocol/lan/TRANSFER_PROFILE.md).

## Connection changes

On Android, Connection details exposes local-network connection controls. The idle file panel presents Send files; when disconnected, that action can start the existing trusted-Mac LAN flow. File selection on both devices requests automatic LAN setup through an existing secured BLE channel when enabled on both devices. The current batch stays on its channel while that channel remains connected, except that a capable local network upgrades an active Bluetooth stream as described below.

Both transports must belong to the same authenticated device. Support and negotiated limits are checked separately on each connection. A new batch prefers a secured local-network channel only after it advertises transfer capability; otherwise a capable Bluetooth channel remains usable. A batch already running on Bluetooth stays there unless local network becomes capable to the same peer, in which case the sender upgrades the active stream in place through the resume handshake. If local network arrives while the sender is between files, the upgrade happens at the next file.

Losing the active connection while a batch is streaming or awaiting approval pauses the batch instead of failing it. Both devices keep their verified partial and last acknowledged offset, show a paused card with frozen progress, and retain job-owned partials and private recovery checkpoints for 15 minutes, including across app restarts. Reconnecting local network to the same peer resumes automatically: the sender requests the retained offset and the receiving side verifies the prefix digest before continuing. If local network stays down while a secured Bluetooth channel exists, either device may choose Continue over Bluetooth. The sending device resumes directly from its acknowledged offset; the receiving device asks the sender to validate the prefix it already holds and stream the rest over Bluetooth, so the receiver never depends on the sender noticing the request. A Bluetooth continuation upgrades to local network automatically when a capable channel appears. Cancel deletes the partial immediately; the 15-minute timeout fails the batch and deletes it. Preparation reserves one job and pins its peer before rendezvous or hashing. macOS waits on capability events with one three-second deadline; cancellation or dismissal retires the wait. Preparation finishes independently of the initiating channel. Interrupted offers retain their batch identity and still require recipient approval. Publication already in progress finishes under its storage owner; verified results remain available to the same peer after reconnection. Files already published remain in place and are not overwritten. Pause is automatic on transport loss; there is no manual pause action while a channel is healthy.

Both apps request LAN for a new send when the active channel is Bluetooth and wait for a bounded rendezvous before offering. A secured LAN is preferred when already ready and upgrades the stream when it becomes capable. With no usable channel, the pending send waits for a bounded connection/capability opportunity; a failed or timed-out LAN request can still use a compatible Bluetooth channel.

Sender progress counts receiver-acknowledged writes; receiver progress counts successful local writes. Rate samples are collected at least 250 ms apart, independently of chunk-driven progress updates. The 21-observation rate window spans about five seconds at that cadence, retaining chunk confirmations through short burst gaps and decaying to zero after a sustained stall.

## Storage and preparation

Mac reception uses the selected folder, exclusive job-owned partials, SHA-256 verification, file synchronization and non-overwriting same-filesystem publication. Storage errors produce failure rather than completion. Existing files and unrelated partials remain untouched.

Android reception opens the system folder picker. Local external-storage and Downloads document providers are accepted only after a disposable read/write/seek/flush/rename/delete probe and available-space check with a 64-MiB reserve. Incompatible providers produce readable feedback. Provider rename is not claimed to be atomic. Persistable grants acquired by the active job are released at cleanup; pre-existing permission modes are retained. Cloud providers are excluded.

Transfer v1 offers include full-file SHA-256, so senders prepare hashes before offering. Preparation runs off the UI thread, is cancellable and displays Preparing files. Streaming completion digests require a separately versioned contract; existing v1 bytes remain unchanged.

Mac normal TCP EOF waits for accepted frame delivery before notifying the connection owner, with a ten-second absolute drain limit. Explicit close and transport or delivery failures retire immediately.

LAN receive backpressure waits between complete frames; frame-bounded socket reads prevent the queue wait from consuming the next frame's ten-second assembly deadline. Transfer DATA and playback traffic share the selected authenticated stream. Records already submitted to TCP remain ordered and cannot be overtaken by a later control command; see the [record-path performance guide](../PERFORMANCE.md).

## Execution and presentation

BLE advertises and uses at most four outstanding chunks, leaving capacity for controls within its eight-message ingress bound. LAN senders negotiating more than 4,096 chunk bytes probe each file/resume with one 4,096-byte chunk before using the full negotiated window. Probe timing starts when encoded bytes enter submission, excluding source reads and encoding; fully drained source idle time is excluded from later ACK-gap detection. Full probe acknowledgement within 100 ms enables large chunks; slower confirmation or a later advancing-ACK gap over one second limits subsequent sender backlog to at most two 65,536-byte chunks within peer credit (128 KiB total). Sustained fallback amortizes per-record security work; the 4-KiB size is used only for qualification probes.

After five seconds since the last probe, a span of at least one second with advancing ACK gaps of at most 100 ms permits a one-chunk drain before a fresh probe. A slower gap or fully drained source idle interval over 100 ms resets qualification without draining the constrained pipeline; a started drain finishes even if its final ACK is delayed. Only a fully confirmed probe within 100 ms restores the negotiated chunk size and window. Each new file and resume starts with a fresh probe; already-submitted TCP bytes remain ordered.

With a negotiated LAN chunk maximum above 4 KiB, each successfully written chunk smaller than that maximum returns credit immediately, including qualification probes and 64-KiB fallback chunks. Full-size chunks retain the quarter-window ACK cadence. Failed ACK submission waits for another capacity or receive event. Successful submission sends newer accumulated credit immediately at the size-based cadence or file end; smaller pending amounts re-arm the 20-ms coalescing timer. Credit waiters are detached before resumption so an inline successor cannot be cleared by the previous wakeup. ACKs identify the active batch/file and cannot exceed admitted bytes. File results must identify the active source and match its digest before success is accepted. Batch-result messages cannot bypass file verification. Empty files finalize without chunks. Offer assembly permits one incomplete inventory for at most ten seconds and validates aggregate counts, byte totals and unique file IDs.

File-confirmation and resume timeouts retain pending work until its original monotonic expiry; capacity events permit another resume attempt with a two-second minimum spacing, without a retry polling loop. Capacity refusal waits for transport events with a bounded timeout; there is no five-millisecond retry loop. Submitted records are not replayed. Progress byte counts are independent of throttled UI updates. Authentication remains in transport order; transfer chunks are admitted to a separate feature-owned FIFO before shared delivery proceeds. File opening, reads, receive writes, SHA-256 updates, synchronization, publication and cleanup execute on IO workers/actors; presentation state stays on its UI owner. Cancellation invalidates the job before callbacks resume. Mac resume abandonment releases its reply continuation and cancels pending request admission; accepted replies allow nonce-owned send completion. Sender source closure rechecks the original epoch before accessing file-result state. Android waits for old storage cleanup before acquiring a successor destination grant. Complete verified partials survive failed publication; corrupt partials are discarded. Capacity refusal emits no synthetic availability event that could wake its own rejected sender.

Android receiver storage uses one shared IO dispatcher with parallelism limited to one, injected through creation and recovery. Per-file mutexes continue to own stream and digest state; provider setup, receiver cleanup and checkpoint writes share the receive dispatcher. Mac storage remains actor-owned. Each receiver queues raw authenticated chunk envelopes with a byte bound of `min(advertised receive chunk bytes × window + 65,536, 2,097,152)` and a record bound of `min(window × 8, 64)`, including the active write. One consumer decodes chunks and receiver resume requests and awaits their storage work in FIFO order. Full capacity suspends ingress; queueing advances neither progress, ACK credit nor successful application activity. Resume bounds its initial wait for accepted work to ten seconds, then verifies and rebinds inside that consumer; later old-channel chunks cannot write across the takeover. Epoch changes invalidate queued work and fence active completions. Normal EOF and authenticated close drain accepted work for at most ten seconds; explicit cancellation, channel replacement and trust retirement invalidate immediately. These feature bounds do not enlarge transport queues or protocol credit. Opt-in storage timing separates Android dispatch/lock wait from storage work and records Mac actor-owned work duration.

Both panels name the peer and the direction of the active batch. A rate that is not yet measurable is presented as unavailable rather than as zero, and an empty batch reports indeterminate progress rather than zero progress. A received file whose bytes have all landed but which is still being hashed and published is presented as verifying and saving instead of as a stalled transfer, and the direction outlives cleanup so a completed batch still reports which way the files moved.

Android starts a connected-device foreground service after a visible user starts sending or approves a destination. Ownership begins during LAN connection and hashing, before the offer is submitted, and continues through destination preflight and streaming. A picker has a separate sixty-second lease; result handling acquires approved work before releasing that lease. Approved LAN and BLE jobs use the transfer service independently of companion ownership. Incoming offers alone do not acquire approved background work.

Android retains one silent connected-device foreground-service notice during approved work. Progress, pauses, completions and failures are presented in the activity panel, without recurring notification updates or terminal alerts. A new incoming offer may post one silent notice when the app is backgrounded, with tap-to-open and Decline. Notification permission does not gate the service; denied permission leaves its required system Task Manager notice. A service failure retires unowned background channels while checkpointed jobs remain pending. Paused work retains bounded transport ownership and explicit Disconnect still wins.

Mac transfer notifications are off by default. Files and Settings → File transfer share optional Background offer notifications and Play sound controls for all phones. Enabled offers post only while aniCe is backgrounded, with Accept, Choose folder and Decline actions bound to their original batch. Pause, reconnection, completion and failure events post no system alerts. Existing transfer banners from older builds are cleared on launch without touching Messages or Find Device notifications. Progress, results and continuation actions remain available in the main window and menu-bar companion. Mac idle-sleep assertions belong to active or paused work.

## Verification

Manual application testing covers transfers in both directions and playback during Phone→Mac transfer. Physical application transfer over a 5 GHz mobile hotspot (external AP) measures 7.0–10.5 MB/s (average ~8.0 MB/s) Mac→Phone, and 3.0–5.2 MB/s (average ~4.0 MB/s) Phone→Mac; an attenuated 2.4 GHz router (3–5m range) measures ~1.0 MB/s symmetrically. Bounded ingress queues and off-main chunk decoding resolve previous progress and rate presentation stuttering.

## Current limits

- Prepared offers, approved streams and verified completion receipts have private recovery journals, bound to the local identity and peer credential. Routine progress checkpoints are spaced at least five seconds apart; pause, file-boundary and publication checkpoints are forced. Receiver checkpoints flush data before recording an offset; recovery rebuilds the prefix digest and discards bytes beyond that checkpoint. Source file boundaries are committed before DATA. Retries and restarts retain the original 15-minute interruption expiry. File selection and unfinished initial hashing are not restored.
- Pause is a consequence of transport loss; there is no manual pause while a channel is healthy, because the peer has no wire message for one.
- A batch only changes transport through the resume handshake to the same authenticated peer: a newly capable LAN upgrades an active Bluetooth stream, and a channel change after a pause rebinds the retained prefix. Either side may initiate a resume; the receiving side always validates it.
- After a local-network pause, Bluetooth continuation requires an explicit action on either device. A paused batch is abandoned after 15 minutes.
- SAF cannot guarantee non-overwriting atomic publication across every provider. A source provider may deny persistent access. Publication interrupted across a provider rename or copy fallback can require checking the destination and sending again; recovery never treats a matching filename alone as proof of publication.

## Implementation

Android implementation and tests live under `features/transfer/`; Mac implementation and tests live under `Features/Transfer/` and `aniCeTests/Transfer/`. TransferDestination owns the Android folder grant and provider probe; TransferService presents approved foreground ownership. The existing connection and session owners retain authentication, nonce ownership and backpressure.
