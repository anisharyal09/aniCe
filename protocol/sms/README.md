# SMS Relay v3

Each DATA plaintext is deterministic RFC 8949 CBOR `["aniCe sms", 3, kind, fields]`, at most 4,000 bytes. Reject non-minimal encoding, indefinite lengths, trailing bytes, invalid UTF-8, extra fields, wrong types, unknown versions/kinds and out-of-range integers. UUIDs are canonical lowercase text; `requestId`/`streamId` are 16 random bytes (RFC 9562 v4). Android produces thread and history data; either side may send a reply. Direction 0/1 in `messageBegin` is from the provider's perspective. Version 3 adds `messageBegin.subscriptionId` and cursor paging for the thread list; v2 peers do not interoperate, so both applications update together.

`dateMillis`, `unreadCount` and both cursors are epoch milliseconds or counts in 0..2^53−1. Message bodies are strict UTF-8 of 1..24,576 bytes with NUL replaced by U+FFFD before encoding; the digest is SHA-256 over the assembled body. `fragmentCount = ceil(totalBytes / 3072)` and all fragments except the last are exactly 3,072 bytes. `unread` is a CBOR boolean.

Capability fields 2 and 3 (`maxThreadsPerPage` and `maxMessagesPerPage`) are the advertiser's limits for the link they were sent on, each in 1..50 and never above the contract maximums; a peer must serve the thread list and requested history or search pages within the limits its peer advertised, so a slower link can announce smaller lists and pages than a local-network one. Both fields are re-sent on every new channel generation, and a request is never rejected for being smaller than the advertised limit.

`threadId` is the provider `thread_id` in decimal or `"addr:<normalized address>"` when no provider row exists; a normalized address is digits with one optional leading `+`, or the trimmed uppercase text for alphanumeric sender IDs (`addr:ACMEBANK`, `addr:AUTH XYZ`), so bank and service senders keep their own conversation. The Mac groups conversations by normalized address, not threadId, so a live-only thread and its later provider thread remain one card. An `addr:` history request selects no provider row, so the phone answers it with an empty terminal page (`nextBeforeMillis = 0` with `nextBeforeMessageId = ""`); the Mac re-requests with the provider threadId once the thread list reports one. `address` is transmitted as stored (raw), truncated on codepoint boundaries; `snippet` follows the same rule.

`messageId` is `"sms:<provider id>"` or `"mms:<provider id>"` for provider rows and `"live:<lowercase hex SHA-256(address || dateMillis || subscriptionId || body)[0..31]>"` for live PDUs; the live form is deterministic so duplicate `SMS_RECEIVED` deliveries collapse, while the subscription keeps two SIM copies of the same text distinct. Implementations compare the full string byte-wise lexically (`"sms:100" < "sms:99"`) and never parse the numeric id. `sendResult.messageId` is a provider ID only on a successful READ_SMS lookup, otherwise `""` and always `""` when `result != 0`. `sendResult.dateMillis` is the reply's send time — the sent row's provider `date` when that lookup succeeds, otherwise the phone's send-queue time — so an echo is never stamped with the moment the radio answered and an incoming answer that arrived during confirmation keeps its newer position.

Results: 0 accepted, 1 disabled (required Android permission missing: READ_SMS for thread/history/search requests, SEND_SMS for a reply, READ_PHONE_STATE for a SIM listing), 2 busy, 3 stale, 4 unsupported, 5 failed, 6 invalid. For a reply, 0 means every multipart `sentIntent` reported `RESULT_OK` — radio acceptance, not recipient delivery. Non-zero results never advance a cursor; only `result = 0` makes `historyDone`/`threadDone`/`searchDone` cursors meaningful.

## Ordering and cursors

Conversation presentation may retain local submit/receive observation order for live messages and their provider copies, independently of carrier clock differences. Display timestamps and protocol cursor ordering remain unchanged.

The thread list is ordered `(dateMillis DESC, threadId DESC)` with the same byte-wise string tie rule as messages and is paged: a request carries the `(beforeMillis, beforeThreadId)` cursor from the previous `threadDone`, and `nextBeforeMillis = 0` with `nextBeforeThreadId = ""` marks the terminal page. Each page carries at most the `maxThreadsPerPage` limit the peer advertised on that link (50 at most); `maxMessagesPerPage` bounds a requested history or search page the same way. History is ordered `(dateMillis DESC, messageId DESC)` with byte-wise lexical messageId comparison, and `(dateMillis, messageId)` exists because MMS seconds collapse to identical milliseconds and carriers split long SMS into rows sharing one timestamp. A row is older than the cursor when `dateMillis < beforeMillis`, or when equal and the messageId (or threadId) compares less than the cursor. An initial request uses `beforeMillis = 0` with an empty cursor id; `nextBeforeMillis = 0` with an empty cursor id means no more pages. Android scans SMS and MMS with independent source positions, filters and orders by timestamp only in SQL and applies the messageId tie-break in Kotlin, because SQLite integer ordering (`99 < 100`) diverges from the lexical contract ordering. A tie group above 2,048 rows returns result 4 without advancing the cursor. An incomplete provider source read returns result 5; failure is never a terminal empty page.

## SIM listing

`simRequest` asks the phone for its active SMS subscriptions and is answered by exactly one `simDone` in which each entry carries the Android subscription ID, the SIM slot index, the user-visible label truncated to 40 UTF-8 bytes on codepoint boundaries and whether the subscription is the phone's default SMS subscription. At most 8 entries are sent; phone numbers are never transmitted. The phone answers result 1 when listing needs its READ_PHONE_STATE permission and it has not been granted. `sendBegin.subscriptionId = 0` sends on the device default; a non-zero value must name an active subscription of the phone or the reply fails with result 4 and is never retried on another subscription. SIM choice is optional: receive, history, search and default-subscription replies work without listing.

Every `messageBegin` carries the subscription that produced the message, so a thread that receives the same sender on two SIMs stays one conversation while each row keeps its origin. `subscriptionId = 0` means unknown (MMS rows and provider rows without a readable subscription id); a client shows SIM labels only when a conversation contains two or more distinct non-zero subscriptions, and providers keep the value opaque beyond display.

## Search

`searchRequest` searches the phone's provider rows — SMS bodies and text/plain MMS parts — and streams matching messages as `messageBegin`/`messageFragment`/`messageCommit` records under the request's `requestId`, terminated by exactly one `searchDone`. Ordering, cursor semantics, tie handling and result codes are identical to history; each hit carries the provider `messageId`, so results deduplicate and merge like any other record. The query is matched as a substring: `LIKE` with `\`, `%` and `_` escaped and ASCII case-insensitivity. A query that is blank after trimming or shorter than 2 UTF-8 bytes is invalid (result 6). Oversized timestamp groups, and a match set larger than the phone's 2,048-message search scan, return result 4 without advancing the cursor, a missing READ_SMS returns result 1, an incomplete provider source read returns result 5, and only `result = 0` advances the cursor. A newer `searchRequest` from the same peer cancels a page in flight, and a mid-page channel loss aborts the page with no `searchDone`. Search results live in memory only on the Mac and are never persisted or re-indexed.

## Flow, acks and failure

Capability must precede traffic on each channel generation: Android sends live events only after the Mac capability, the Mac requests only after the Android capability, and both re-send capability on every new channel. A capability record is idempotent, so a peer that has not received the other's capability may send it again, and the receiver answers a capability record with its own; a hello lost in either direction is therefore recovered without waiting for a new channel generation. One thread-list, one history page, one search page and one outgoing reply are in flight per peer, with 30-second LAN and 60-second BLE deadlines; stale request/stream IDs are ignored. A history page is a sequence of `messageBegin`/`messageFragment`/`messageCommit` records terminated by `historyDone`.

Live events are acknowledged with `messageResult`; only result 0 from an attempted authenticated peer/channel confirms receipt, transient errors remain retryable and disabled/unsupported/invalid results terminate the event; history pages are covered by `historyDone` alone and per-message history acks are omitted. A mid-page channel loss aborts the page with no `historyDone`; the Mac re-requests from its last completed cursor. Live delivery prefers LAN, falls back to an already-secured BLE channel, and retries once on the other live channel after failure. An unacknowledged event is offered again inside its pending lifetime (every few seconds) instead of waiting for the next channel generation, and a peer whose capability has not been received is asked to advertise again on that link. Replies are fragmented by the Mac and reassembled by Android under the transport-specific deadline before sending; Android emits `sendResult` only after every part `sentIntent` reports `RESULT_OK`, a part fails, or the request deadline expires. Result 5 after telephony submission is unconfirmed and must not trigger automatic resending. Completed reply request IDs retain at most 32 results per connected peer for ten minutes; duplicate commits return the recorded result, and the cache is cleared on the last channel retirement. A reply with no live channel fast-fails; replies are never queued or persisted.

Rows 1..24,576 bytes are transmitted; oversized provider bodies are skipped and counted, never truncated, and one skipped row must not fail a page. With no live channel, Android keeps at most 16 pending live events for 10 minutes and flushes them on the next channel; nothing survives process death on either platform, and an incoming SMS may request the existing bounded automatic LAN attempt.

## Deduplication and merge

Live events are deduplicated for 10 minutes by messageId; a one-to-one content key `(normalized address, direction, SHA-256 body, dateMillis ±5 s, subscription)` merges provider and live copies when the subscriptions agree or either one is unknown (0). Distinct live IDs are not collapsed solely because their bodies match, and two SIMs that receive the same text at the same moment keep two rows. The content key lets a live PDU copy merge with the provider row the default SMS app writes asynchronously: the provider `sms:`/`mms:` record wins and replaces the `live:` copy in the Mac thread view, and an already-posted notification is left untouched. Notifications are posted exactly once per previously unknown live message; history refreshes post none.

## Permissions and privacy

Android live relay needs RECEIVE_SMS, threads/history/search need READ_SMS, replies need SEND_SMS and an optional SIM listing needs READ_PHONE_STATE; result 1 carries the distinction. Neither platform writes SMS content to disk and neither logs bodies, addresses or search queries; the Mac keeps peer data in memory only and clears it when the peer's last link retires, trust is removed or the app quits. No contacts lookup (no READ_CONTACTS) and no read-state mutation occur; `unreadCount` counts unread incoming provider rows (the threads view's `read` column is an all-read flag, never a count) and viewing history does not mark SMS read. MMS support is limited to text/plain parts: group MMS (more than one recipient) and attachment-only messages are detected and reported unsupported rather than guessed, and MMS send is impossible through public Android APIs.
